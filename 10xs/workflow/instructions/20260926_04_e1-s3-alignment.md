# Microtask Instruction: e1-s3 — 16 KB native alignment check

## Objective

Give the shared `readiness_check` library a way to determine whether every
native `.so` file inside a plugin's package archive is 16 KB page-aligned:
read each one's ELF program headers and confirm every `PT_LOAD` segment's
alignment is at least `0x4000` (16384 bytes).

## Context

- Builds on e1-s2 (`packages/readiness_check`, merged to `develop` at
  `9233677`): `package_archive.dart` already decodes a package archive
  (gzip-then-tar, via `package:archive`) but only exposes entry *paths*
  (`listArchiveEntryPaths`), discarding file contents. This check needs the
  actual bytes of each `.so` entry, so `package_archive.dart` needs a second,
  generic entry point that returns content for entries matching a predicate.
- SPEC §3.1.2: "for every `.so` file inside the package archive, read the ELF
  program headers and check that each `LOAD` segment's alignment is at least
  16 KB (0x4000)."
- SPEC §3.2: the board "shows the evidence behind its colour: the file found,
  or the misaligned library and its alignment" — so the result for a
  misaligned `.so` must carry which file and what its actual alignment is,
  not just a boolean.
- SPEC §4: "v1 only sees `.so` files shipped inside the pub.dev archive" — no
  APK/AAB inspection, no Maven/CocoaPods native libraries. This microtask's
  scope is exactly the archive bytes `package_archive.dart` already decodes.
- ELF layout reference (both 32-bit and 64-bit must be supported — Android
  ships both `armeabi-v7a`/`x86` 32-bit and `arm64-v8a`/`x86_64` 64-bit
  libraries): the ELF identification bytes at offset 0 are `0x7f 'E' 'L' 'F'`;
  byte 4 (`EI_CLASS`) is `1` for ELF32 / `2` for ELF64; byte 5 (`EI_DATA`) is
  `1` for little-endian / `2` for big-endian. The program header offset,
  entry size and count (`e_phoff`, `e_phentsize`, `e_phnum`) sit at fixed
  offsets that differ between ELF32 (28/42/44) and ELF64 (32/54/56). Each
  program header's type (`p_type`, first 4 bytes) and alignment (`p_align`,
  last 4 or 8 bytes of a 32-byte ELF32 / 56-byte ELF64 header) are what this
  check reads; `p_type == 1` is `PT_LOAD`.

## Implementation Steps

1. `lib/src/package_archive.dart` — add `extractArchiveEntries(archiveBytes,
   predicate)`: decodes the archive the same way `listArchiveEntryPaths`
   does, and returns a `Map<String, List<int>>` of entry path to raw content
   for every entry whose path satisfies `predicate`. Keep
   `listArchiveEntryPaths` as-is; both share the same decode, so factor the
   gzip+tar decode into a private helper used by both.
2. `lib/src/elf_alignment_check.dart` (new) —
   - `class ElfAlignmentResult`: `path` (String), `aligned` (bool),
     `minLoadSegmentAlignment` (nullable int — the smallest `PT_LOAD`
     `p_align` found, in bytes; null if the file has no `PT_LOAD` segment).
   - `class NotElfException implements Exception`: thrown by
     `checkSoAlignment` when the given bytes don't start with the ELF magic
     number; carries the offending path.
   - `bool isSharedLibraryPath(String path)`: `path.endsWith('.so')` — the
     "which archive entries are `.so` files" predicate, exported so the
     caller can pass it straight to `extractArchiveEntries`.
   - `ElfAlignmentResult checkSoAlignment(String path, List<int> bytes)`:
     parses the ELF header (32-bit and 64-bit, either endianness) and every
     program header, and returns the result described above.
     `aligned` is true when every `PT_LOAD` segment's `p_align` is
     `>= 0x4000`, per SPEC §3.1.2's literal wording (a segment with
     `p_align` of `0` or `1` — "no particular alignment" in the ELF spec —
     is therefore reported as misaligned, matching how Android's own
     alignment-check tooling reads this field).
   - `List<ElfAlignmentResult> checkPackageAlignment(Map<String, List<int>>
     soFileContents)`: runs `checkSoAlignment` over each entry.
3. `lib/readiness_check.dart` — export the new public symbols.
4. `test/elf_alignment_check_test.dart` — build minimal synthetic ELF32 and
   ELF64 byte buffers in test setup (no fixture binaries committed, no
   network — same approach e1-s2 used for its in-memory tar.gz), covering:
   - a 64-bit LOAD segment aligned at exactly `0x4000` -> `aligned: true`;
   - a 64-bit LOAD segment aligned below `0x4000` (e.g. `0x1000`) ->
     `aligned: false`, with `minLoadSegmentAlignment` reporting the actual
     value;
   - a 32-bit LOAD segment, both aligned and misaligned;
   - multiple LOAD segments where only one is misaligned -> `aligned: false`
     reporting the smaller of the two;
   - bytes that don't start with the ELF magic -> `NotElfException`.
5. `test/package_archive_test.dart` — add coverage for
   `extractArchiveEntries`: returns content only for entries matching the
   predicate, and an empty map when nothing matches.

## Acceptance Criteria

- `checkSoAlignment` correctly parses both ELF32 and ELF64 headers and
  reports every `PT_LOAD` segment's alignment against the `0x4000` (16 KB)
  threshold from SPEC §3.1.2.
- A misaligned result carries the actual alignment found
  (`minLoadSegmentAlignment`), so the board can show "the misaligned library
  and its alignment" per SPEC §3.2.
- `extractArchiveEntries` reuses the same decode path as
  `listArchiveEntryPaths` rather than duplicating it.
- No implementation file exceeds 150 lines.
- `dart analyze` is clean and `dart test` passes with zero network calls.

## Testing Strategy

Unit tests only, all offline: `elf_alignment_check_test.dart` builds
synthetic ELF32/ELF64 byte buffers by hand (header + program headers with
chosen `p_align` values) rather than shipping real `.so` fixtures — real
aligned/misaligned fixture libraries are e6-s1's scope (recorded fixtures),
not this microtask's. `package_archive_test.dart` extends the existing
in-memory tar.gz round-trip pattern to cover `extractArchiveEntries`.
