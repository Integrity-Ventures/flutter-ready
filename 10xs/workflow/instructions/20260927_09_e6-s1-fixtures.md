# e6-s1: Fixtures (architect, 2026-09-27)

Read `00_ARCHITECT_GATE.md` and the e6-s1 section of
`20260927_05_architect-notes-e2-e6.md` first. This instruction fills in the
detail that note leaves to the seat: which real packages to capture, which
state gets a synthetic fixture and why, and where the alignment samples come
from.

## Objective

Give `readiness_check`'s own test suite (and, later, e6-s2's golden CLI
tests) a shared, on-disk fixture set so no test ever calls pub.dev (SPEC
§5). Today every test in `packages/readiness_check/test/` builds its input
inline (literal tag lists, in-memory tar bytes, a hand-built ELF byte
array) — that works, but it means the "recorded pub.dev API response" and
"sample .so file" fixtures SPEC §5 asks for don't exist anywhere as
artifacts a person or e6-s2 could point at directly.

## Context

- Card e6-s1 checklist item `e6-s1-mt1`: "Fixture plugins and recorded
  pub.dev API responses. One fixture per readiness state (SwiftPM present,
  absent, tag/archive disagreeing) plus aligned and misaligned sample `.so`
  files; tests never call the network."
- Architect note e6-s1: `packages/readiness_check/test/fixtures/`, include
  one federated plugin set (app-facing plus `_ios` and `_android`).
- The fleetbox has live network access to pub.dev, so "recorded" fixtures
  can be captured for real rather than invented, except for the
  disagreement state, which has no known stable, reproducible real
  instance to pin as a fixture (SPEC cites flutter/flutter#187330 as the
  general class of bug, not a specific still-disagreeing plugin).
- This card does not touch the root-level `fixtures/sample_app/` directory
  or `.github/workflows/verify-action.yml` — the 2026-09-27 architect note
  scoped that rework into e6-s2.

## Implementation steps

1. Capture real pub.dev responses for the federated `url_launcher` /
   `url_launcher_ios` / `url_launcher_android` set (SwiftPM present state)
   and for `flutter_barcode_scanner` (SwiftPM absent state — real,
   unfederated, last published 2021, pre-dates SwiftPM). Save
   `GET .../score` and `GET .../<name>` (trimmed to `name` + `latest`) as
   `test/fixtures/pub_dev/<package>_{score,info}.json`.
2. Fabricate one synthetic package, `fixture_swiftpm_disagree`, whose score
   fixture is tagged `is:swiftpm-plugin` but whose archive fixture has no
   `Package.swift` — the disagreement state, since no real one could be
   pinned.
3. Write `test/fixtures/generate_fixtures.dart`, a regeneration script
   (not itself a test) that:
   - builds two minimal synthetic ELF `.so` files (one `PT_LOAD` segment
     each, 64-bit, no code — same technique as
     `test/elf_alignment_check_test.dart`'s inline builder) at `0x4000`
     (aligned) and `0x1000` (misaligned) alignment, saved under
     `test/fixtures/so_files/`;
   - packs trimmed-but-real archive fixtures for `url_launcher_ios`
     (`pubspec.yaml` + its `Package.swift`), `url_launcher_android`
     (`pubspec.yaml` + its real `build.gradle.kts`, which is also the
     "no native libs in archive" alignment case), and
     `flutter_barcode_scanner` (`pubspec.yaml` + its real podspec + its
     real Groovy `build.gradle`) — file contents embedded verbatim from
     the real archives, trimmed of IDE metadata, example apps and gradle
     wrapper jars the checks never read;
   - packs the synthetic `fixture_swiftpm_disagree` archive (podspec only,
     no `Package.swift`) and a synthetic `fixture_alignment_plugin`
     archive (a real Gradle file plus one aligned and one misaligned `.so`
     from step 3a, so `checkPackageAlignment` has a mixed-result archive).
4. Write `test/fixtures/fixture_loader.dart`: `fixtureBytes`,
   `fixtureJson`, `fixtureTags` helpers reading from
   `test/fixtures/` relative to the package root (`dart test`'s cwd).
5. Write `test/fixtures_test.dart` exercising `checkSwiftPmReadiness`,
   `checkPackageAlignment`, `checkSoAlignment` and
   `extractAndroidBuildSettings` against the fixtures for all three
   SwiftPM states, the federated set, the mixed-alignment archive and the
   two Android Gradle dialects.
6. Document provenance (what's real vs. synthetic, capture date, why) in
   `test/fixtures/README.md`.
7. Leave every existing test file in `packages/readiness_check/test/`
   untouched — this card adds a fixture pool, it doesn't migrate existing
   inline tests onto it.

## File scope

- `packages/readiness_check/test/fixtures/generate_fixtures.dart` (new)
- `packages/readiness_check/test/fixtures/fixture_loader.dart` (new)
- `packages/readiness_check/test/fixtures_test.dart` (new)
- `packages/readiness_check/test/fixtures/README.md` (new)
- `packages/readiness_check/test/fixtures/pub_dev/*.json` (new, data)
- `packages/readiness_check/test/fixtures/sources/**` (new, plain-text data
  `generate_fixtures.dart` reads and packs — kept as separate files rather
  than string constants so each is individually readable and diffable)
- `packages/readiness_check/test/fixtures/archives/*.tar.gz` (new, generated)
- `packages/readiness_check/test/fixtures/so_files/*.so` (new, generated)
- `packages/readiness_check/analysis_options.yaml` (edit: exclude
  `test/fixtures/sources/**`, since a fixture `pubspec.yaml` is otherwise
  linted by `dart analyze` as a real package manifest)

One implementation file (`fixture_loader.dart`) plus one test-tooling
script (`generate_fixtures.dart`, excluded from the implementation-file cap
as test tooling) and one test file; everything else is fixture data.

## Acceptance criteria

- `dart analyze --fatal-infos` and `dart test` both pass in
  `packages/readiness_check` with zero network calls made by any test.
- All three SwiftPM readiness states (present, absent, disagreeing) are
  each backed by a fixture and asserted in `fixtures_test.dart`.
- The federated `url_launcher` set is present and used for the SwiftPM
  present case, per the federation rule.
- At least one aligned and one misaligned `.so` fixture exist and are
  asserted both standalone and inside a package archive.
- `README.md` states which fixtures are real captures (with capture date
  and source version) and which are synthetic, and why.
- `generate_fixtures.dart` reproduces the committed binaries byte-for-byte
  when re-run (no non-determinism — no timestamps/random data in the
  archive or ELF builders).

## Testing strategy

`dart analyze --fatal-infos packages/readiness_check` and
`dart test packages/readiness_check` (via `cd packages/readiness_check &&
dart test --reporter expanded`, matching `ci.yml`). No live network calls
during test runs — the pub.dev captures above happen once, at fixture-authoring
time, via plain `curl`, not from Dart test code.
